Ваш прогресс

Как думать на экзамене

  1. Деньги, безопасность, compliance — только детерминированно. Hook или программный гейт, а не инструкция в промпте. У промпта всегда ненулевой процент отказа.
  2. Пропорциональный первый шаг. Если описания инструментов или критерии в промпте слабые, сначала исправь их. Классификатор, роутер или отдельная ML-модель почти всегда избыточны.
  3. Ищи причину выше по течению. Если сабагенты честно сделали свою часть, а результат неполный, виновата декомпозиция координатора.
  4. Ошибки должны быть структурированными. Тип сбоя, что пытались, частичные результаты, retryable или нет. Пустой результат — это успешный запрос, а не сбой. Глушить ошибку и ронять весь workflow одинаково плохо.
  5. Минимальные привилегии для агентов. 4–5 инструментов на роль. Для частого кросс-ролевого случая дай узкий инструмент, сложные случаи веди через координатора.
  6. Правильный scope конфигурации. Общее для команды кладётся в проект и коммитится (.claude/, .mcp.json). Личное хранится в ~/.claude. Правила для файлов, разбросанных по репо, оформляются как .claude/rules/ с glob в paths.
  7. «Модель побольше», «окно побольше», «ещё ретраи», «поднять max_tokens» — обычно дистракторы. Они не устраняют корневую причину.
  8. Самооценка уверенности и сентимент — плохие прокси сложности. Эскалацию калибруют явными критериями с few-shot примерами.
  9. Ревью делает независимый экземпляр. Сессия, которая писала код, хуже находит в нём ошибки. Большие ревью разбивай на проход по каждому файлу и отдельный интеграционный проход.
  10. Batch API только для неблокирующих задач. −50% стоимости, до 24 часов, без SLA, без многоходового tool calling внутри запроса, сопоставление по custom_id.

Шесть сценариев

Ключевые факты по доменам

D1 · Агентная архитектура

  • stop_reason "tool_use" → выполнить инструмент и продолжить; "end_turn" → закончить. Не парсить текст и не ставить лимит итераций как основной стоп.
  • Результаты инструментов добавляются в историю, модель видит их на следующей итерации.
  • Hub-and-spoke: вся связь между сабагентами идёт через координатора.
  • Сабагенты не наследуют контекст. Всё нужное передаётся в промпте, метаданные (URL, страницы) отдельно от контента.
  • Сабагенты запускает Task tool, allowedTools координатора должен включать "Task". Параллельный запуск = несколько Task-вызовов в одном ответе.
  • PostToolUse нормализует результаты. Перехват исходящих вызовов блокирует нарушения политик, например refund больше $500.
  • --resume <name>, если контекст ещё актуален. Новая сессия с summary, если результаты инструментов устарели. fork_session для сравнения двух подходов.

D2 · Инструменты и MCP

  • Описание инструмента — главный механизм выбора: форматы входа, примеры, граничные случаи, чем отличается от соседнего инструмента.
  • Ошибки MCP: флаг isError, errorCategory (transient / validation / permission / business), isRetryable.
  • tool_choice: "auto" (может ответить текстом), "any" (обязан вызвать какой-то инструмент), forced {"type":"tool","name":…}.
  • .mcp.json — проект, общий для команды, с ${TOKEN}. ~/.claude.json — личные и экспериментальные серверы. Инструменты всех серверов доступны одновременно.
  • MCP resources открывают каталоги (схемы, документацию, задачи) без лишних исследовательских вызовов.
  • Grep ищет по содержимому, Glob по путям. Edit требует уникального якоря, иначе Read + Write.

D3 · Claude Code

  • Иерархия CLAUDE.md: user (~/.claude/CLAUDE.md, не шарится), project, directory. @import для модульности. /memory показывает, что загружено.
  • .claude/rules/*.md с paths: (glob) грузится только при работе с подходящими файлами.
  • Команды: .claude/commands/ (команда, git) и ~/.claude/commands/ (личные).
  • Skills: .claude/skills/*/SKILL.md, frontmatter context: fork, allowed-tools, argument-hint. Skills вызываются по требованию, CLAUDE.md загружен всегда.
  • Plan mode для архитектуры и многофайловых изменений. Direct execution для ясной точечной правки. Explore-сабагент изолирует многословный поиск.
  • CI: -p, --output-format json, --json-schema. Ревью делает независимый экземпляр. Прошлые находки передаются в контекст, чтобы не дублировать комментарии.

D4 · Промпты и структурированный вывод

  • Явные категориальные критерии работают, а «будь консервативен» не повышает точность. Шумную категорию можно временно отключить, чтобы вернуть доверие.
  • Few-shot: 2–4 примера на неоднозначные случаи, с объяснением, почему выбран именно этот вариант.
  • tool_use + JSON schema убирает синтаксические ошибки, но не семантические: суммы не сходятся, значение не в том поле.
  • Nullable-поля защищают от выдуманных значений. В enum добавляй "unclear", "other" + detail.
  • Retry с конкретной ошибкой валидации помогает при ошибках формата. Если данных в источнике нет, retry бесполезен.
  • Batch: −50%, до 24 часов, без SLA, custom_id. Повторно отправляй только упавшие запросы.

D5 · Контекст и надёжность

  • Блок «case facts» (суммы, даты, номера заказов) хранится вне суммаризируемой истории.
  • Lost in the middle: ключевые выводы ставь в начало, разделы помечай заголовками. Ответы инструментов обрезай до нужных полей.
  • Эскалация нужна, когда клиент просит человека (сразу), политика молчит или есть исключение, прогресса нет. Несколько совпадений → запросить дополнительный идентификатор.
  • Сбой доступа ≠ пустой результат. Сабагент чинит transient-ошибки сам и передаёт наверх только то, что не смог.
  • Долгие сессии: scratchpad-файлы, /compact, сабагенты для поиска, манифесты состояния для восстановления после сбоя.
  • Общие 97% могут скрывать провал на одном типе документов. Нужна стратифицированная выборка и уверенность по полям, откалиброванная на размеченных данных.
  • Сохраняй связи claim → source и даты публикации. Конфликтующие данные показывай оба с атрибуцией.
